# Nota técnica — Mesa247 Waiting List

## 1. Tres preguntas al diseñador

**1. ¿Qué ocurre si el comensal no responde después de ser llamado?**
Asumí que el anfitrión lo llama y pasa de `WAITING` a `CALLED`, registrando `called_at`. Se consideran los 10 minutos comunicados en el flujo, pero no implementé automatizaciones adicionales para mantener el MVP simple.

**2. ¿La actualización de la cola necesita ser en tiempo real?**
Asumí que unos segundos de diferencia son aceptables para el piloto. Implementé polling silencioso cada 10 segundos y actualización inmediata después de una acción. WebSockets quedan fuera del primer corte.

**3. ¿WhatsApp y el reporte diario deben estar automatizados desde esta versión?**
Asumí que no son necesarios para validar el flujo principal. WhatsApp se representa mediante un enlace manual `wa.me` y el reporte diario mediante una vista dentro de la aplicación. La integración automática con WhatsApp y el envío del reporte por email quedan desacoplados para una evolución posterior.

## 2. Qué construyo primero y qué corto

Prioricé un vertical slice completo:

`Comensal se registra → entra a la cola → anfitrión ve la cola → llama al siguiente`

Estimación:

| Parte                                            | Tiempo |
| ------------------------------------------------ | -----: |
| Modelo + persistencia                            | 30 min |
| API y reglas de cola                             | 60 min |
| Vista comensal                                   | 45 min |
| Vista anfitrión                                  | 45 min |
| Tests críticos                                   | 30 min |
| Integración, Docker/Cloud Run, README y revisión | 30 min |

**Core:** registro, cola activa y llamar al siguiente.

Como extensiones, si el tiempo lo permite: posición/estado, sentar/cancelar/no-show, reporte diario, enlace manual de WhatsApp y drag & drop.

Corto del MVP: WhatsApp automático, emails, WebSockets, integración PHP legado y automatizaciones avanzadas de no-show.

## 3. Modelo de datos

```text
Restaurant
- id
- name
- created_at

        1
        │
        N

QueueEntry
- id
- restaurant_id
- name
- phone
- party_size
- status
- created_at
- called_at
```

La posición no se persiste: se calcula sobre los registros `WAITING` ordenados por llegada. Así evito mantener posiciones mutables y dejo la base de datos/backend como fuente de verdad.

## 4. Qué devolvería al diseñador

Además de las pantallas funcionando, devolvería las decisiones que aparecieron al convertir el diseño en comportamiento real.

Explicaría qué quedó dentro del flujo principal, qué resolví provisionalmente —polling, WhatsApp manual y reporte como vista— y qué necesita definición de producto antes de automatizarlo.

La intención sería que el siguiente diseño ya incorpore esos estados y casos límite, no solamente devolver el desarrollo terminado.

## 5. Decisiones difíciles de cambiar después

Evitaría hacer irreversibles decisiones que todavía no necesitamos.

Especialmente cuidaría:

* no acoplar la cola a Meta, Twilio u otro proveedor;
* no persistir la posición como un número mutable;
* mantener backend/BD como fuente de verdad;
* no acoplar el dominio a SQLite;
* mantener estable el significado de los estados de la cola.

SQLite se utiliza por simplicidad local, pero el modelo queda preparado para MySQL en producción.

## 6. Cómo lo llevaría a producción

El backend FastAPI está preparado para ejecutarse como contenedor en **Google Cloud Run**, utilizando el `PORT` proporcionado por la plataforma. En producción utilizaría MySQL administrado y configuración/secrets externos al repositorio.

El frontend React se genera mediante Vite y puede servirse como contenido estático/CDN; también se dejó un preset de contenedor mediante Nginx.

El flujo de despliegue sería:

`tests → build → imagen → deploy → health check`

Las migraciones se ejecutarían de forma controlada y no durante el arranque de cada instancia.

Monitorizaría como mínimo disponibilidad, errores 5xx y latencia, junto con logs estructurados y un health check externo.

Si el sistema se cae un viernes a las 9 p. m., una alerta automática debería avisarme sin depender de un reporte de usuario. A partir de ella utilizaría logs y métricas centralizadas para identificar si el fallo proviene de la aplicación, la base de datos o la infraestructura.

La prioridad para este piloto es una solución pequeña, observable y fácil de evolucionar, antes que introducir infraestructura que todavía no aporta valor.
