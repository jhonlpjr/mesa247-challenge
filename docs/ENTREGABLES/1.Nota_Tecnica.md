# Nota técnica — Mesa247 Waiting List

## 1. Qué validaría antes de construir

Antes de cerrar el comportamiento definitivo del producto, confirmaría con diseño/producto tres puntos:

### ¿Qué ocurre si un comensal es llamado y no responde?

Para el piloto asumo que pasa de `WAITING` a `CALLED` y se registra `called_at`. No automatizaría todavía el vencimiento: el anfitrión mantiene el control operativo. El modelo permite evolucionar posteriormente a `NO_SHOW` y políticas configurables por restaurante.

### ¿La cola necesita tiempo real estricto?

Para el piloto asumo que no. Con un máximo aproximado de 40 personas en cola por local, tablets compartidas y conectividad Wi-Fi deficiente, utilizaría HTTP con polling silencioso cada 10 segundos. Es más simple de operar y suficiente para validar el flujo. WebSockets/SSE se evaluarían después con métricas reales de uso.

### ¿WhatsApp y el reporte diario son parte obligatoria del primer corte?

Asumo que no forman parte del camino crítico. El piloto prioriza administrar correctamente la cola. WhatsApp queda desacoplado para una integración posterior y el reporte diario puede evolucionar sin afectar el dominio principal.

---

## 2. Qué sale primero y qué corto

El objetivo del primer corte es validar el flujo que genera valor inmediatamente:

**Comensal se registra → aparece en la cola del restaurante → anfitrión visualiza la cola → llama al siguiente.**

Priorizo aproximadamente:

| Trabajo | Estimación |
|---|---:|
| Modelo y persistencia | 30 min |
| API y reglas principales | 60 min |
| Flujo comensal | 45 min |
| Flujo anfitrión | 45 min |
| Tests críticos | 30 min |
| Integración, ejecución y documentación | 30 min |

El MVP utiliza React + TypeScript y FastAPI, con SQLite para facilitar la ejecución local y una arquitectura preparada para MySQL en producción.

No intentaría resolver en este corte integración completa con WhatsApp Business, SMS, sincronización con el sistema PHP existente, WebSockets, automatizaciones avanzadas de `NO_SHOW` ni una plataforma de reporting completa.

Algunas extensiones —estados adicionales, reporte diario y acciones manuales relacionadas con WhatsApp— pueden estar presentes en la implementación como demostración, pero no las considero necesarias para demostrar el núcleo solicitado.

## 3. Modelo y decisiones principales

El modelo mínimo separa al restaurante de sus entradas de cola:

```text
Restaurant
- id
- name
- country_code
- phone_country_code
- timezone
- created_at

QueueEntry
- id
- restaurant_id
- name
- phone
- party_size
- status
- created_at
- called_at
- seated_at
- cancelled_at
```

La relación `restaurant_id` evita mezclar colas entre locales y permite que cada restaurante tenga configuración propia.

La **posición no se persiste**. Se deriva de las entradas `WAITING` y su orden. Guardarla como un número fijo introduciría inconsistencias cada vez que alguien es llamado, cancelado o abandona la cola.

El backend es la fuente de verdad. El frontend presenta el estado y solicita acciones, pero no decide reglas de transición ni el orden definitivo de la cola.

También considero desde el inicio el caso de los **dos anfitriones utilizando tablets simultáneamente**. Dos solicitudes concurrentes de “llamar siguiente” no deberían seleccionar la misma entrada. En local puede utilizarse una protección sencilla; en MySQL la garantía debería resolverse transaccionalmente, por ejemplo mediante bloqueo de la fila candidata dentro de una transacción.

## 4. Del piloto a la operación real

El contexto conocido condiciona varias decisiones aunque no todas necesiten implementarse ahora.

### Tres locales y expansión por países

El piloto empieza con tres locales, pero Mesa247 opera en Perú, Chile, Ecuador y Colombia. Por eso el restaurante es una entidad explícita y puede almacenar país, prefijo telefónico y zona horaria.

La evolución sería convertir estas diferencias en configuración y no introducir reglas específicas por país dentro de la interfaz.

### Sistema PHP existente

No acoplaría el nuevo flujo directamente al modelo interno del sistema legacy durante el piloto. Primero validaría que la nueva lista de espera resuelve el problema.

Si debe convivir posteriormente con locales, mesas o reservas existentes, introduciría una API o adapter claramente delimitado entre ambos sistemas.

### Conectividad deficiente

Mantendría HTTP y polling como primera opción. Añadiría timeouts, reintentos seguros, estados de error claros e idempotencia donde corresponda.

Solo introduciría WebSockets/SSE si la operación real demuestra que los 10 segundos de actualización son insuficientes.

### WhatsApp Business y SMS

Las notificaciones deberían implementarse detrás de un puerto/adapter, evitando que el dominio dependa de Meta o de un proveedor concreto.

Una siguiente fase incorporaría templates aprobados, reglas y tarifas por país, registro del resultado del envío y eventualmente SMS como fallback.

Esto permite cambiar de proveedor sin modificar el flujo principal de la cola.

### De 3 a 150 locales

No diseñaría infraestructura para una escala que todavía no existe, pero evitaría decisiones que impidan alcanzarla.

FastAPI puede mantenerse stateless y escalar horizontalmente en Cloud Run; los datos permanecen aislados por restaurante y MySQL sería la persistencia de producción.

Antes de la expansión mediría latencia, volumen de requests, conexiones a base de datos y comportamiento del polling para ajustar capacidad con datos reales.

## 5. Qué devolvería a diseño/producto

Después del piloto devolvería evidencia concreta, no solo comentarios:

- tiempos reales de espera;
- frecuencia de actualización necesaria;
- comportamiento cuando alguien no responde;
- acciones que más utiliza el anfitrión;
- errores de conectividad;
- feedback de los tres locales.

Con esos datos validaría especialmente el significado visual de los estados, comportamiento de `NO_SHOW`, información realmente necesaria para el anfitrión, cuándo notificar al comensal y si el polling resulta suficiente.

Esto permitiría que la siguiente iteración responda a comportamiento observado y no a supuestos previos.

---

## 6. Decisiones costosas de cambiar después

Intentaría mantener estables desde el inicio:

- separación de datos por restaurante;
- backend como fuente de verdad;
- posición derivada y no almacenada;
- contratos HTTP independientes de la interfaz;
- reglas de negocio fuera de React;
- proveedor de notificaciones detrás de una abstracción;
- timestamps suficientes para reconstruir la historia de una entrada;
- configuración de país y timezone asociada al restaurante.

En cambio, polling, proveedor de WhatsApp, frecuencia de actualización, UI concreta y estrategia de reporting son decisiones que deberían poder evolucionar sin rediseñar el dominio.

## 7. Producción y cómo sabría si falla un viernes a las 9 p. m.

Para producción desplegaría el backend en **Google Cloud Run**, manteniéndolo stateless, y utilizaría **MySQL administrado**.

El frontend podría servirse como contenido estático/CDN o mediante el preset de Cloud Run preparado en el proyecto.

Las migraciones se ejecutarían de forma controlada durante el despliegue y secretos/configuración permanecerían fuera del repositorio.

Como mínimo observaría:

**disponibilidad → errores HTTP → latencia → conexiones/errores de base de datos → fallos al llamar siguiente.**

Expondría un health check y configuraría alertas por incremento sostenido de errores `5xx`, indisponibilidad o latencia anormal.

Los logs deberían ser estructurados e incluir identificadores como `restaurant_id` y operación, evitando datos personales innecesarios.

Así, si el servicio falla un viernes a las 9 p. m., no dependería de que un restaurante reporte el problema: la monitorización debería detectarlo, alertar y permitir identificar rápidamente si el origen está en Cloud Run, la aplicación o la base de datos.
